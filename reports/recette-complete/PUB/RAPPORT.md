# Recette PUB — Site public, connexions et droits d'accès

Agent : PUB · serveur testé : http://localhost:3210 (branche `codex/prep-pr-main`) · rapport généré le 17/11/2026 08:03:18 · 280 cas enregistrés dans `resultats.json`.

## 1. Synthèse

**Ce qui marche.** Les 18 pages publiques et de connexion s'affichent sur ordinateur, tablette, Android, iPhone et petit écran, sans défilement horizontal, sans erreur JavaScript ni réponse 5xx. L'accueil (navigation, menu mobile, champ « Ouvrez votre dossier », badges de bail, visite guidée, tarif, FAQ, contact, rechargement), le simulateur, les 24 articles du blog et leurs 8 calculateurs fonctionnent. Les connexions par code (propriétaire, locataire, notaire) fonctionnent sur les trois appareils, avec refus des codes faux, anciens ou expirés, et les déconnexions invalident bien la session.

**Droits d'accès : cloisonnement solide entre comptes existants.** Sur 190 appels d'API croisés et une centaine de pages ouvertes avec chaque rôle fictif, aucune donnée d'un autre dossier n'a été obtenue : un client ne lit ni le bail, ni le bien, ni les pièces, ni la messagerie d'un autre ; le notaire ne voit que le dossier qui lui est attribué ; un visiteur est partout renvoyé à la connexion.

**Ce qui ne marche pas — un défaut bloquant.** N'importe quel visiteur peut se créer un compte **administrateur** : la page `/register` (liée depuis `/login`) et la route `/api/auth/sign-up/email` créent un compte dont le rôle par défaut en base est `ADMINISTRATEUR`, et la session est ouverte d'office. Vérifié trois fois avec des comptes fictifs, neutralisés ensuite. Le code en cause est identique sur `staging` et sur `main`.

**Le reste est mineur** : anciennes routes de connexion encore exposées, annuaire public des adresses (client / notaire / équipe), refus d'API renvoyés en 500 au lieu de 401/403, page de maquette `/testFiches` publique, ancre morte du pied de page, bouton « S'abonner » sans effet, image manquante dans un article, bulle « Support » qui mord sur le bouton principal sur iPhone, montants négatifs au simulateur, quelques messages techniques en anglais.

**Verdict.** Le site public et les connexions sont prêts ; les corrections de la branche n'ont rien cassé sur ce périmètre (aucun défaut d'origine « branche » trouvé). En revanche l'inscription publique doit être fermée avant toute mise en production — et vérifiée sans attendre sur la production actuelle, puisque `main` porte le même code.

### D1. Un visiteur peut se créer un compte administrateur (inscription publique ouverte)

- **Gravité** : bloquant · **Origine** : staging (code identique sur main) · **Appareil(s)** : tous (défaut côté serveur) · **Confirmé** : oui, trois fois (deux par l'écran, une par appel direct)
- **Comment le reproduire** : 1) Sans être connecté, ouvrir `/register` (lien « Pas encore de compte ? » de `/login`). 2) Saisir un nom, une adresse e-mail quelconque, un mot de passe, laisser le rôle proposé, « Créer un compte ». Variante sans écran : `POST /api/auth/sign-up/email` avec `{ email, password, name }`.
- **Ce qu'on attendait** : Aucune création de compte publique : la page n'existe pas ou l'inscription est refusée ; les comptes de l'équipe sont créés par un administrateur.
- **Ce qu'on voit** : Message « Compte créé avec succès! ». Le compte est créé en base avec le rôle `ADMINISTRATEUR` (ce n'est pas le rôle choisi à l'écran, c'est la valeur par défaut de la colonne) et le visiteur est **déjà connecté** sans autre étape. Avec ce compte : `/interface` s'ouvre, la fiche d'un dossier s'affiche, `GET /api/clients/<id>` renvoie la fiche complète d'un client (forme : `{ id, type, profilType, completionStatus, persons, entreprise, documents, bails, … }`), `/interface/clients` répond 200, et la route de changement de rôle (réservée aux administrateurs) lui obéit. Contrôle fait uniquement sur des dossiers fictifs ; aucune donnée réelle ouverte ni capturée. Les trois comptes de recette créés ont été ramenés au rôle `UTILISATEUR` sans client rattaché (ils n'ouvrent plus rien : `/interface` → `/login`).
- **Capture** : `captures/inscription-publique-formulaire.png`, `captures/inscription-publique-resultat.png`, `captures/inscription-publique-acces-dossier-fictif.png`
- **Code soupçonné** : `lib/auth.ts` (`emailAndPassword: { enabled: true }` sans `disableSignUp`) ; `prisma/schema.prisma` (`User.role @default(ADMINISTRATEUR)`) ; `app/register/page.tsx` (page active : le bloc « désactivée » est en commentaire, le formulaire réel est au-dessous) ; `app/login/page.tsx` (lien vers `/register`). `git diff staging` : aucun écart sur ces fichiers ; sur `main`, la page, le défaut `ADMINISTRATEUR` et l'inscription par mot de passe sont déjà présents.
- **Cas** : PUB-330, PUB-331, PUB-332

### D2. Anciennes routes de connexion par code encore exposées

- **Gravité** : mineur · **Origine** : staging · **Appareil(s)** : serveur · **Confirmé** : oui (appel + lecture du code)
- **Comment le reproduire** : Sans session : `POST /api/auth/client/request-otp { email }` puis `POST /api/auth/client/verify-otp { email, code }`.
- **Ce qu'on attendait** : Routes supprimées (l'écran de connexion ne les utilise plus) ou protégées comme la connexion officielle.

- **Code soupçonné** : `app/api/auth/client/request-otp/route.ts`, `app/api/auth/client/verify-otp/route.ts` (et leurs équivalents `notaire/`).
- **Cas** : PUB-426

### D3. Annuaire public des adresses : on peut savoir si une adresse est celle d'un client, d'un notaire ou de l'équipe

- **Gravité** : mineur · **Origine** : staging · **Appareil(s)** : serveur · **Confirmé** : oui, deux passes
- **Comment le reproduire** : Sans session : `POST /api/auth/client/check-user { email }`, `POST /api/auth/notaire/check-user { email }`, `POST /api/auth/client/prepare-login { email }`.
- **Ce qu'on attendait** : Même réponse que l'adresse soit connue ou non.
- **Ce qu'on voit** : Réponses `{ exists: true, isClient: true }` pour un client, `{ exists: true, isNotaire: true }` pour un notaire, `{ exists: true, isNotaire: false }` pour une adresse de l'équipe, `{ exists: false }` pour une inconnue ; `prepare-login` répond 403 / 404 selon le cas. Aucune limite de débit constatée. Les écrans de connexion disent de même « Aucun compte trouvé pour cet email » ou « Cet email n'est pas associé à un compte notaire ». La route voisine `/api/clients/check-email` a pourtant été fermée pour éviter cet annuaire.
- **Code soupçonné** : `app/api/auth/client/check-user/route.ts`, `app/api/auth/notaire/check-user/route.ts`, `app/api/auth/client/prepare-login/route.ts`.
- **Cas** : PUB-425, PUB-301, PUB-310

### D5. Refus d'accès renvoyés avec un statut 500 au lieu de 401 / 403 / 404

- **Gravité** : mineur · **Origine** : staging · **Appareil(s)** : serveur · **Confirmé** : oui, deux passes
- **Comment le reproduire** : Appeler sans droit `/api/properties/<id>`, `/api/clients/<id>`, `/api/client/properties/<id>`, `/api/bail/<id>/messages` (GET et POST), `/api/bail-messages/send-with-s3`, `/api/notaire-requests/add-document-with-s3`.
- **Ce qu'on attendait** : 401 sans session, 403 sans droit, 404 si l'objet n'existe pas.
- **Ce qu'on voit** : Le refus a bien lieu (aucune donnée renvoyée), mais avec un statut 500 et le texte de l'exception (« Unauthorized », « Forbidden », « Non autorisé », « Demande introuvable »). Ces faux 500 se mêleront aux vraies pannes dans la supervision. De même, un corps de requête illisible sur `/api/blob/get-signed-url` donne 500.
- **Code soupçonné** : Routes `app/api/properties/[id]`, `app/api/clients/[id]`, `app/api/client/properties/[id]`, `app/api/bail/[bailId]/messages`, `app/api/bail-messages/send-with-s3`, `app/api/notaire-requests/add-document-with-s3` : le `catch` renvoie toujours 500.
- **Cas** : PUB-401, PUB-402, PUB-403, PUB-404, PUB-405, PUB-423

## 4. Observations (hors défauts)

- **Mesure d'audience sans consentement.** Google Analytics (identifiant de production) est chargé sur toutes les pages par `app/layout.tsx`, sans bandeau de consentement ; des appels vers `analytics.google.com` et `ad.doubleclick.net` partent dès la première page. Pendant la recette, les navigateurs de test ont donc envoyé des mesures à Google depuis `localhost` : c'est la seule chose qui soit sortie de la machine, et cela pollue un peu les statistiques de production.
- **Deux estimations différentes des frais notariés.** L'accueil annonce « ≈ la moitié du loyer » (900 € → ≈ 450 €, total 489,90 € avec les frais de dossier), le simulateur ajoute les procurations et 20 % de TVA (950 € → 594 € TTC, sans frais de dossier). Un visiteur qui passe de l'un à l'autre voit deux prix.
- **Champ « Ouvrez votre dossier ».** Tant que l'adresse n'est pas plausible, le bouton reste grisé sans aucun message ; une faute de frappe ne donne aucun indice.
- **Lenteurs.** Premier affichage de l'accueil à froid : 11,7 s sur ordinateur et 8,1 s sur iPhone ; ensuite 2 à 3 s. Les autres pages publiques s'affichent en 1,6 à 2,2 s, les articles en 0,3 à 1,3 s.
- **Annuaire pour tout compte connecté.** `/api/clients/check-email` répond « existe / n'existe pas » à n'importe quel client connecté, pour n'importe quelle adresse (prévu par le code).
- **Point d'entrée des tâches de fond.** `GET /api/inngest` décrit la configuration (nombre de fonctions, présence des clés) et un `POST` non signé renvoie une erreur 500 contenant une pile d'exécution. Sur ce montage les tâches sont des doublures : à revérifier en production.
- **Redirections d'un utilisateur déjà connecté.** Elles se font côté navigateur après un court délai (une à plusieurs secondes sous charge), pendant lequel le formulaire de connexion reste affiché. `/client/login` et `/notaire/login` ne prévoient de renvoi que pour le rôle administrateur : le cas des opérateurs et réviseurs n'a pas pu être joué (pas de compte fictif).
- **Déconnexion.** Depuis l'espace client on arrive sur l'accueil ; depuis l'espace notaire, sur `/notaire/login`, sans message de confirmation ; depuis l'équipe, sur `/login`. L'ancien cookie est refusé dans tous les cas.
- **Accessibilité.** Pas de lien « aller au contenu » ; focus visible sur tous les arrêts de tabulation de l'accueil et des connexions ; libellé « Support » de la bulle à 4,2:1 ; logo du pied de page bleu foncé sur fond sombre, peu lisible ; images de l'accueil avec texte alternatif vide.
- **Divers.** Pied de page « © 2025 » en novembre 2026. Portraits des témoignages et visuels du blog servis par des hébergeurs tiers (pexels, unsplash). `manifest.webmanifest` absent (404). Une bascule « Type de bail » est codée en boutons radio : lisible au clavier.
- **Liens sortants relevés (non visités)** : `tel:0768098624`, `mailto:contact@bailnotarie.fr`, `https://ec.europa.eu/consumers/odr/`.

## 5. Non testé, et pourquoi

- Détail de l'accueil sur tablette et petit écran : seuls l'affichage des 18 pages, le menu et la bulle y ont été vérifiés ; les treize vérifications détaillées de l'accueil ont été jouées sur ordinateur, Android et iPhone.
- Appareils : les « téléphones » sont des navigateurs Chromium (Pixel 7) et WebKit (iPhone 13) émulés par Playwright, pas des appareils physiques.
- PUB-600 — Envoi réel d’un commentaire d’article : Il exige une vérification reCAPTCHA auprès de Google : service externe, et un automate ne doit pas la contourner. Seuls la lecture et le refus sans jeton ont été vérifiés (PUB-266).
- PUB-601 — Recherche d’entreprise aboutie (/api/intakes/<jeton>/company-lookup avec une session de formulaire) : L’appel abouti interroge l’annuaire des entreprises, hors de la machine. Seuls les refus (jeton inconnu, soumis, sans code, autre client) ont été vérifiés (PUB-417).
- PUB-602 — Notaire appelant le zip ou la fiche d’un dossier attribué à un AUTRE notaire : Mes données ne comptent qu’un notaire fictif et une seule attribution. Vérifié à la place : le notaire est refusé sur tout ce qui touche le dossier 1, non attribué (messages, parties, pièces, canal temps réel, dépôt).
- PUB-603 — Session expirée par le seul passage du temps : La durée de vie d’une session se compte en jours. Vérifié à la place : session invalidée par déconnexion (ancien cookie refusé), cookie inventé, cookie à signature fausse.
- PUB-604 — Blocage après un trop grand nombre de codes faux : Règle de la recette : trois essais faux au plus par adresse. Deux codes faux par adresse ont été refusés proprement ; le seuil de blocage n’a pas été cherché.
- PUB-605 — Rôles opérateur et réviseur : connexion et redirections : Aucun compte fictif de ces rôles dans mes données (un seul compte équipe, administrateur). À la lecture du code, /client/login et /notaire/login ne redirigent que le rôle administrateur.
- PUB-606 — Appels directs des actions serveur (hors routes /api) : Les actions serveur de Next.js s’appellent par un identifiant interne propre à chaque build ; les rejouer hors de l’écran demandait un outillage dédié, hors du temps imparti. Les agents de chaque espace les exercent par l’interface.
- PUB-607 — Vérification de signature de /api/inngest en production : Sur ce montage les tâches de fond sont des doublures locales, en mode développement : le refus d’un appel non signé ne peut se vérifier qu’en production.
